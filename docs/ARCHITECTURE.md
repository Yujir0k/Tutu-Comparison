# Архитектура

## Цели

Система оптимизирована под три свойства: правдивость данных, объяснимость рекомендации и быстрый ответ. Архитектура намеренно не содержит LLM в критическом пути: выбор строится детерминированными функциями, поэтому результат воспроизводим и тестируем.

## Компоненты

### Клиент

React отвечает за форму поиска, состояние выдачи, фильтры, shortlist и сравнительные таблицы. Отельный сценарий выделен в `src/features/hotels`, переиспользуемые контролы — в `src/components`. Клиент не обращается к MCP напрямую и не хранит доверенные данные.

### API

Express является anti-corruption layer между браузером и Tutu MCP:

1. принимает небольшой JSON-запрос;
2. нормализует и проверяет его в `server/validation.ts`;
3. параллельно запрашивает независимые транспортные источники;
4. применяет чистые функции scoring;
5. возвращает стабильный типизированный контракт;
6. при кратком отказе использует только ранее полученный реальный ответ.

### Правила

`src/scoring.ts` и `src/hotelScoring.ts` не выполняют I/O. Компоненты оценки нормализованы, неизвестные данные не получают положительных баллов, а tie-breakers заданы явно. Версия правил возвращается вместе с транспортной выдачей.

### Кэш

Файловый кэш подходит для одной VPS-инстанции и не является источником истины. Ключ — SHA-256 от нормализованного запроса. Запись атомарная, чтение защищено от повреждённого JSON, хранение ограничено 250 файлами и семью днями.

## Поток отказа

- Один транспорт недоступен: `Promise.allSettled` сохраняет остальные результаты и сообщает недоступный режим.
- Все транспортные источники или поиск отелей недоступны: API проверяет свежий кэш точного запроса.
- Кэша нет: клиент получает безопасную понятную ошибку и может повторить запрос.
- MCP отвечает слишком долго или слишком большим payload: запрос прекращается установленным лимитом.

## Границы масштабирования

Текущая архитектура рассчитана на одну или несколько независимых stateless API-инстанций, если кэш не обязан быть общим. Для горизонтального масштабирования rate limit и fallback-кэш следует перенести в Redis/S3-совместимое хранилище. Scoring и UI изменений не потребуют.

## Ключевые решения

- Детализация номера удалена намеренно: после выбора отеля пользователь переходит к оригинальному Туту, поэтому локальный дубль booking flow создавал бы расхождение данных.
- Production-сервер компилируется в JavaScript; `tsx` используется только в разработке и тестах.
- Прогрев MCP после старта сокращает холодный первый запрос, но не влияет на readiness приложения.
